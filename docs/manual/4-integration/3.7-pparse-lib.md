## 3.7 Pparse Lib

The `lib` package is the foundational layer of pparse. It defines the types that every parser and every view is built on: the I/O abstractions that reach into files, the reader types that scope and navigate within them, the extraction that couples bytes to results, the node that holds one unit of parsed data, and the parser that drives interpretation. Nothing in `lib` knows about any specific binary format, it provides the vocabulary that format-specific code writes in.

### 3.7.1 Data, Cursor, and Range

Reading from a binary file requires two distinct concerns: owning the access to persistent storage (the file handle, the HTTP session, the in-memory buffer), and tracking where you currently are within that storage (the offset). Pparse separates these into **Data** and **Cursor**.

A **Data** object owns the I/O backend. Its one required method is `peek(cursor, length)`, read `length` bytes at the position indicated by the cursor, without advancing any offset. `read(cursor, length)` and `seek(cursor)` have default implementations built on `peek`. Concrete implementations include `FileData` (reads a local file via `seek` + `read` syscalls), `BytesIoData` (wraps an in-memory `BytesIO` buffer), and `HttpCachedData` (fetches remote content via HTTP with a chunk cache). All three expose an optional `length` attribute set at construction.

A **Cursor** is a stateful read pointer into a `Data`. It holds a reference to the `Data` and a current byte offset. When you call `cursor.read(n)`, the cursor delegates to `data.peek(cursor, n)` and then advances its `_offset` by the number of bytes returned. `cursor.seek(offset)` and `cursor.skip(n)` update the offset and call `data.seek(cursor)` to sync any internal file pointer the `Data` maintains. `cursor.peek(n)` reads without advancing.

The reason `Data` does not track offset itself is that a single `Data` object is shared across every reader derived from it. Multiple parsers, multiple nodes, and the caller may all hold independent cursors into the same file. If `Data` held the offset, a read from one cursor would silently corrupt the position seen by every other.

A **Range** wraps a `Cursor` and adds boundary enforcement. When you know that a particular structure spans exactly `n` bytes starting at the current position, you construct a `Range(cursor, n)`. The `Range` clamps all `seek`, `skip`, `peek`, and `read` calls to the half-open interval `[start, start + n]`, so the parser operating inside it cannot accidentally read past the end of that structure. `range.left()` returns the number of bytes remaining between the current position and the end. `range.dup()` returns an independent copy at the same position, used to hand child parsers a reader they can seek freely without moving the parent's cursor.

```text
Data  <-----  FileData / BytesIoData / HttpCachedData
 │
 └── Cursor  (owns offset, delegates I/O to Data)
      │
      └── Range  (wraps Cursor, enforces [start, start+length])
```

Both `Cursor` and `Range` implement the **Reader** interface: `tell()`, `seek()`, `skip()`, `peek()`, `read()`, and `dup()`. Parser code is written against `Reader` wherever possible so that either type can be substituted.

### 3.7.2 Extraction

An **Extraction** is a named pairing of a data source with the parse results derived from it. It holds a human-readable name (typically a filename), a `_result` dictionary that maps string keys to root `Node` objects, and a small `_extractions` list for any child extractions derived from the same underlying data. The name is meaningful: it is what `match_extension` tests against when auto-detecting the right parser.

**BytesExtraction** is the concrete subclass used in practice. It is backed by an existing `Reader` — either the full-file `Range` created by a view, or a sub-range passed down when parsing a nested structure. Its `open()` method returns `self._reader.dup()`, giving each caller an independent reader at position zero.

The `_result` dictionary is where parsed trees live. When a view's internal parse sequence calls `extraction.add_result('json', root_node)`, by convention it registers the root `Node` under the key `'json'`. After `root_node.load()` completes, `extraction._result['json']` is the root of the fully populated parse tree. The view's `root_node()` method reads from exactly this slot. The string key is a format identifier, not a filename — the same `BytesExtraction` could hold results under multiple keys if the same bytes were parsed by more than one parser (though this is uncommon).

An `Extraction` has no reference back to its `Node`s. The nodes reference the extraction's `Reader` indirectly (via their own `NodeContext`), but the extraction holds only the root node reference per slot. Whether nodes below the root remain alive is determined by who holds a reference to them, typically the caller or the `NodeContext._descendants` list during loading.

### 3.7.3 Node

A **Node** is one unit of the parse tree. Every region of binary data that a parser identifies as a distinct structure (a JSON object, a protobuf message, a flatbuffers table, a scalar leaf), becomes a `Node`.

When a `Node` is created it receives a `Reader` positioned at the start of its data region and a `Parser` that knows how to interpret it. Its `_value` starts as **UNLOADED_VALUE**, a module-level sentinel that is distinct from every legitimate parsed value including `None` and `0`. The `value` property checks for this sentinel: if it is still `UNLOADED_VALUE`, it calls `self.load()` before returning `_value`. This makes loading lazy by default, a `Node` defers work until something accesses `.value`.

`load()` is where the parser state machine runs. It loops calling `state.parse_data(self)` on the current state, using the return value to decide what to do next. When a state returns `AGAIN` the loop continues with whatever state is now on top of the stack. When a state returns `ASCEND`, the loop exits, this node is done. In between iterations, `load()` drains `self.ctx()._descendants`: for every child `Node` a state registered there, `load()` calls `child.load()` before proceeding to the next state iteration. This implements depth-first traversal without recursion within a single `load()` call — the iteration over `_descendants` is just a queue drain.

`set_length(length)` replaces the node's `Reader` with a `Range` of exactly `length` bytes. This is called by states that know a structure's byte span in advance (protobuf `LEN` fields, flatbuffers tables) after calling it, `ctx.left()` becomes meaningful. `clear_ctx()` releases the `NodeContext` to free memory; it should only be called once the node's value is fully loaded and re-parsing is no longer needed.

### 3.7.4 NodeContext

Every `Node` owns a **NodeContext**. The `NodeContext` is the coupling object between the node and its `Parser`; it holds everything a state needs to parse one node's bytes:

- `_reader` — an independent copy of the node's `Reader`, positioned at the node's start
- `_state_stack` — the active state objects; `state()` returns the top
- `_parent` — the parent `Node`, or `None` for the root
- `_descendants` — a list of child `Node` objects created during parsing, drained by `load()`
- `_parser` — the `Parser` responsible for this node
- `_start`, `_end` — byte offsets marking the node's extent

The state stack is managed by `_next_state(StateClass)`, which replaces the top-of-stack state with a new instance of `StateClass`. States are instantiated fresh each time they are set, so they can accumulate internal state across multiple `parse_data` calls (a JSON number parser, for instance, collects digits across successive calls until it sees a non-digit byte). `_pop_state()` removes the top state and lets the one below it take over, used by `NEXT`-returning states.

Format-specific `NodeContext` subclasses add format-specific fields. The protobuf context adds `_type_desc` (the schema descriptor for the current message type); flatbuffers adds `_vtable_offset`, `_vtable_size`, `_field_offsets`, and `_field_count`; JSON adds `_key_reg` (a scratch register for map keys awaiting their paired value). These are specified at `Node` construction time via `ctx_class=FormatNodeContext`.

A `NodeContext` has a `left()` method that returns bytes remaining in the node's data region, but only when the node's `_reader` is a `Range`. Calling `left()` on a `Cursor`-backed reader raises an exception. The distinction matters: root nodes start with a full-file `Cursor`; child nodes whose byte span is known at creation time receive a `Range`. States that need `left()` are always operating on a `Range`.

The `NodeContext` also provides passthrough `peek()`, `read()`, `seek()`, `skip()`, and `tell()` methods that forward to `_reader`. Parser states call these rather than reaching through to the `Reader` directly, so the `NodeContext` acts as a single point of indirection that can later be archived or replaced without changing the state code.

```text
Node
 ├─ _reader  (Reader at node's start offset)
 ├─ _value   (UNLOADED_VALUE -> dict | list | scalar after load())
 └─ _ctx: NodeContext
     ├─ _reader      (dup of node's reader)
     ├─ _state_stack [ State, ... ]
     ├─ _parent      (parent Node or None)
     ├─ _descendants [ child Node, ... ]  <- drained by load()
     └─ _parser      (Parser)
```

### 3.7.5 RecursionControl

`load()` accepts an optional **RecursionControl** that bounds how deeply it recurses into descendants. A `RecursionControl` carries `min_depth` (always recurse below this level), `max_depth` (never recurse above this level), and a `callback` that can inspect each node and return `True` to stop recursion there. Without a `RecursionControl`, `load()` expands the entire reachable tree.

`RecursionControl` is stateful: `increase_depth()` and `decrease_depth()` are called on entrance to and exit from each `load()` call, including on exception paths via `finally`. This means a single instance tracks depth accurately even through exceptions. It also means an instance cannot be reused across independent `load()` calls — the depth counter starts from whatever state the previous call left it in, not from zero.

`RecursionControl.max_seen_depth` records the high-water mark of recursion depth observed across its lifetime. This is useful for debugging: after a load, `recursion.max_seen_depth` tells you how deep the format went.

### 3.7.6 Parser

A **Parser** is the abstract driver for a specific binary format. It holds a reference to the `Extraction` it is consuming and a string `_id` that identifies it within that extraction. Concrete subclasses override three things:

- `match_extension(fname)` — returns `True` if the filename extension suggests this parser handles the data.
- `match_magic(cursor)` — returns `True` if the magic bytes at the start of the data identify the format.
- `make_root_node()` — creates and returns the root `Node` for the extraction, with its initial state set.

The base `Parser.__init__` optionally receives a `base_state_cls`. When provided, it discovers all subclasses of that class at construction time and registers them in `_all_states` by name. This allows states to be specified as strings (e.g. when reconstructing a parse session from XML), not just as class references. `_init_state_as_cls(init_state)` resolves either form to the actual class.

The `Parser` does not hold the `Node` tree — that lives in the `Extraction._result` dict. The `Parser` is a stateless factory, state machine driver, and utility library, not a data store. Once `make_root_node()` and `load()` complete, the parser's work is done and the tree is navigable without it.

### 3.7.8 Control flow constants and exceptions

When a state's `parse_data(node)` call returns, it uses one of three integer constants to signal what should happen next:

- `AGAIN` — the state machine transitioned; continue the loop on the same node with the new state.
- `ASCEND` — this node is fully parsed; exit the loop and return to the caller (or the parent node's `load()`).
- `NEXT` — like `AGAIN`, but first pop the top state off the stack if there is more than one state pending.

The framework defines four exceptions. `EndOfDataException` is raised when the data source runs out of bytes unexpectedly — it propagates up through `load()` and is treated as a fatal parse error. `EndOfNodeException` is the signal for a normal, expected end of parsing at the current node — `load()` catches it silently and treats it as equivalent to `ASCEND`. `UnsupportedFormatException` is raised when the bytes do not match the expected format — also propagated, not caught. `BufferFullException` is raised when a buffer-based component cannot accept more data; currently used in limited contexts.

The distinction between `ASCEND` and `EndOfNodeException` is historical: `ASCEND` is the return-value protocol used by the current state machine design, while `EndOfNodeException` is a legacy pattern from an earlier implementation that used exceptions for normal control flow. Both are caught and handled correctly by `load()`.

### 3.7.9 The public API surface

The `__init__.py` exports all of the above under `thirdparty.pparse.lib`, which is the single import the lazy and view layers use:

```python
import thirdparty.pparse.lib as pparse
```

Everything discussed in this section: `Data`, `FileData`, `BytesIoData`, `HttpCachedData`, `Cursor`, `Range`, `Reader`, `Extraction`, `BytesExtraction`, `Node`, `NodeContext`, `RecursionControl`, `Parser`, `Tensor`, `AGAIN`, `ASCEND`, `NEXT`, `EndOfDataException`, `EndOfNodeException`, `UnsupportedFormatException`, `BufferFullException` is available on that module.
