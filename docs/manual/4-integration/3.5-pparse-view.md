## 3.5 Pparse Views

When you use pparse to examine a binary model file, a common interaction is through a **view** — a format-specific class that wraps all the internal steps of setting up a data source, selecting a parser, and materializing a parse tree, and exposes the result through a purposeful interface. The view package provides one view class per supported format.

Each view class exposes the same two entry points: `open_fpath(fpath)`, which reads from a file on disk, and `from_bytesio(bytes_io)`, which reads from an in-memory `BytesIO` buffer. Both methods return the view itself, so the loaded state is retained by the object rather than returned separately.

When you call either entry point, the view constructs an **Extraction**, which is the object that couples the raw bytes to the parser that will interpret them. An `Extraction` holds two things: a `Reader`, which is a cursor-based interface into the underlying bytes, and a result dictionary that maps format keys to the root of the parse tree once parsing is complete. The `Extraction` is the internal coupling object; you do not interact with it directly after loading.

With the `Extraction` in place, the view instantiates the appropriate parser and calls `parser.make_root_node()` to produce the root **Node**, a placeholder that starts in an unloaded state. That root `Node` is registered in the extraction's result dictionary under a key specific to the target format. Then `root_node.load()` is called, which drives the parser to walk the raw bytes and fill the node tree. By the time `open_fpath` or `from_bytesio` returns, the tree is materialized for dereferencing.

After loading, the entry point for further work is `root_node()`, which returns the root `Node` of the parse tree. A `Node` has a `.value` property that holds the parsed content. At interior positions, `.value` is a `dict` mapping field names to child `Node` objects, or a `list` of child `Node` objects. At the leaves, `.value` is a scalar (a string, integer, or `bytes` object). Navigation is by chaining `.value` accesses. For example, to reach the list of graph operators in an ONNX file, you write `onnx.root_node().value['graph'].value['node']`. Each intermediate object in that chain is a `Node`. `.value` must be called at each level to unwrap the next (and potentially continue stopped parsing).

```text
View
 └─ Extraction
     ├─ Reader  (cursor into the raw bytes)
     └─ result dict
         └─ root Node
             ├─ .value → dict  →  { 'field': Node, ... }
             └─ .value → list  →  [ Node, ... ]
                  └─ .value → scalar
```

`load()` accepts an optional **RecursionControl**, which limits how deeply the parse tree is eagerly expanded. A `RecursionControl` takes a `min_depth` (always expand nodes below this depth), a `max_depth` (never expand nodes above this depth), and an optional `callback` that receives each node and can return `True` to stop expansion at the given depth. Without a `RecursionControl`, `load()` expands the entire tree (i.e. parsed the entire file in memory all at once). For large files where only a header is needed, a shallow `RecursionControl` avoids materializing the full tree. `RecursionControl` tracks depth as internal state while descending. Note: A single instance must not be reused across multiple `load()` calls.

### 3.5.1 Format variants and built-in schemas

The view package contains two kinds of views. The first kind are **schema-free**. The format is self-describing, so no additional input is needed to load it. You get back a `root_node()` whose structure mirrors the file's own layout. Schema-free formats include JSON, XML, ZIP, and so forth.

The second kind are **schema-driven**. The format is an encoding of a typed schema, and the parser needs the schema to interpret the bytes. For `Onnx`, `TFLite`, and `MNN`, the view bundles its own schema internally, so callers don't provide one. To use the more generic `flatbuffers` or `protobuf` parsers, you supply the schema file path and any other arguments (e.g. starting message type).

### 3.5.2 The Tensor interface

For formats that store tensors, the view exposes a higher-level interface alongside the parse tree. After loading, `tensor_names()` returns a list of tensor name strings present in the file. `tensor(name)` returns a **Tensor** object for a named tensor.

A `Tensor` provides a format-independent interface to tensor data (i.e. ML parameters):

- `get_type()` returns the dtype as a safetensors-compatible string: `"F32"`, `"I64"`, `"U8"`, and so on.
- `get_shape()` returns the list of dimensions.
- `get_data_bytes()` returns the raw bytes exactly as stored.
- `as_numpy()` returns a `numpy.ndarray` with the appropriate dtype and shape.
- `as_array()` returns a Python tuple via `struct.unpack`, useful where numpy is undesirable.

A `Tensor` is a lightweight view object, not a buffer. Calling `tensor(name)` does not copy the tensor data into memory, it creates an object that knows how to locate and decode the data on demand. The actual bytes are read when you call `get_data_bytes()` or a decoding method. For large language model weight files where individual tensors can exceed a gigabyte, this keeps memory usage proportional to what you actively decode, not to the total file size.

A `Tensor` has no reference back to the root `Node`. The parse tree and the tensor interface are parallel views of the same underlying bytes: the parse tree exposes every field the format defines, while the `Tensor` interface surfaces only what's relevant to numerical computation. For inspection and format archaeology, `root_node()` is the complete picture. For computation tasks, `tensor()` is the right entry point.

The `Tensor` base class defines `get_type()`, `get_shape()`, `get_data_bytes()`, `as_array()`, and `as_numpy()` as the interface each format-specific subclass must implement. The type strings are deliberately matched to the safetensors convention so that tensor metadata can be compared or relayed across format boundaries without an intermediate translation step.
