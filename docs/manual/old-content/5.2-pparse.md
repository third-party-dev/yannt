# Pparse

## Plugins

Pparse consumes entrypoints from `[project.entry-points."pparse_command"]`. All upstream plugins are built into the code base because thus far the only dependencies have been flatbuffers, protobuf, and numpy. If more heavy dependency trees would be required for a specific plugin, that plugin would be extracted into its own package.

## Pparse Plugin (High Level) Components

All pparse sub commands (or plugins) have several interfaces to be concerned with.

- `lazy` API - The lazy parsing is the whole point of pparse ... lazily parse files and be as forgiving as possible about lack of data, resources, or integrity. If a plugin doesn't have or utilize a lazy API, it should be put outside the scope of pparse.

  - Its worth noting here that the _true_ intentions of the `lazy` API are to enable the recursive parsing of a tree of files and file containers (e.g. zip). This functionality is still baked into the design of the API, but the applicable use has taken a back seat while a collection of formats are fleshed out.

  - Another primary goal of the lazy parsers is to be knowledgeable about the more tedious parts of a file and allow for skipping that section of parsing until explicitly requested by the user. The way this may be handled is very format specific and often not achievable in more generic formats. While a goal, this deferral functionality has been ironically deferred. Note: Any deferred sub-trees of the parsed data would be marked with `pparse.UNLOADED_DATA`.

- `view` Class - The `view` classes are an abstraction from the low level interfaces of the `lazy` API. When I initially cut the `lazy` API for use and developed several parsers, I realized that it was _way_ to complex for a data scientist to want to use. Upon receiving user feedback, it was discovered that the users wanted an easy way to extract "things of value" from the relevant files. For example, in model files you'd want to be able to query tensors, the tensor parameters, and the computation graph of the model.

  - In the specific case of model formats, a `Tensor` Class API has started to form. The idea is to provide:
    - Tensor name list
    - Tensor object fetch by name
    - Tensor params as python array
    - Tensor params as numpy array

- `cli` registration - Whether there is only a `lazy` API or a `view` Class, `cli` sub commands can be registered for quick use by users. CLI commands are naturally flexible, but there are some conventions that I've used throughout.

  - `--breakpoint` - When this flag is provided as an argument to `pparse`, if the registered CLI sub command supports it, it'll dump local variables and throw a breakpoint() that launches pdb after parsing but before exit. This allows runtime inspection of parsed objects.
  - `--print` - If supported, intended to recursively print a string representation of the parsed Node tree of a particular result. Often matched with the STDOUT redir pattern: `yannt pparse <format> view --print path_to_file.bin > file-dump.out`
  - `view` sub commands should use the `view` Class.
  - `parse` sub commands are for parsing via means other than `view` class (e.g. `lazy API`)

## Node Tree Print Outs

I've been using a funky node tree string representation that is a mix of XML and JS/JSON. The idea is that JSON doesn't have descriptive element names or attributes, so I inject those into the data for extract context. For example:

```xml
<NodeMap offset="34">{
    key1: value1,
    key2: <NodeArray offset="45">[
        value2,
        value3,
    ]</NodeArray>,
}</NodeMap>
```

This format is a great balance between low code maintenance and descriptiveness. I'd like to find some easy ways to mutate the data for more use in more tools, for example stripping the XML elements and having the result be pure yaml or json.

One great use of this format is VSCode. You can easily fold up all of the elements with `Ctrl+K` + `Ctrl+0` and then manually traverse each of the XML elements and inner key values. This type of workflow is a lot more smooth for analysis and discovery than typing everything into pdb or python.

## thirdparty.pparse.lib

By convention I often use:

```python
import thirdparty.pparse.lib as pparse
```

pparse contains all of the low level base classes (or API). Use of the low level API for lazy parsers is recommended/required to have any hope of integrating into the parallelized/recursive parsing system that pparse intends to realize.
