## Docs Documentation

- The intention is to have the manual broken up into:
  - Executive Summary
  - End User Docs (CLI Users)
  - Integration Docs (Jupyter/Python Users)
  - Tutorials - For _common_ step by step use cases.
  - API Reference
    - Python Code (including yannt, hft, pparse, analysis, and naive packages)
      - Auto-generated documentation from source code docstrings.
    - Build System (Bash/Python) - TBD
    - Rust - TBD
  - Maintainer - For developers and contributors of upstream yannt code.

### CommonMark Markdown

The goal is to have all of the documentation in a CommonMark friendly markdown that is as legible as reasonable in markdown form, but also intentionally legible and easy on the eyes when rendered into:

- Common Markdown viewers - For example the markdown viewer in VSCode.
- PDF (via pandoc)
  - I want to be able to reasonable reference API documentation on printed material and not hate what I'm seeing.
  - I want to be able to reasonably have a PDF viewer and use hyperlinks in the document in offline systems.
  - Note: PDF handling has a higher priority than HTML handling.
- React (via Docusaurus)
  - I want docusaurus to be able to render the markdown appropriately.
  - There are a number of changes to docusaurus configuration and custom.css to make this doable, and that is acceptable.
    - One of the largest changes includes a new sidecar TOC for the API documentation that overrides the auto generated (via markdown header) TOC for each page.
- HTML (via pandoc)
  - I want to be able to optionally view the page in simple browser environments (VSCode internal browser, webviews, and terminal browsers).
  - I want to be able to print the HTML version and have page grouping considered when determining page breaks.
  - Note: Because PDF has higher priority to HTML, things like page consistency or an unusable TOC in HTML to PDF conversion is considered acceptable.
- ePub (via pandoc)
  - I want to be able to reasonably read the documentation in black and white eInk.
  - There is an emphasis on use of color and style in PDF, HTML, and Reach. When using eInk, these style may be omitted.
  - Ideally, linking should work in ePub as well.
  - I have no intention to support non-open standards of ePub.
  - Color or detailed diagrams may (acceptably) remain not legible in eInk scenarios lacking color, space, or DPI.
- Others (via pandoc)
  - Info pages, man pages, docx should work reasonably well if ePub and PDF are sufficiently mature.

Because of the restricted nature of Markdown, the goal is to enhance the readability in various viewers (not raw markdown) with minimal HTML elements sprinkled in, but only were its considered necessary:

- Horizontal Rules cross the viewable area (not some 50% line that does nothing for your eyes scanning the area.)
- Multiple horizontal rule thickness. It can be very advantageous to have thicker rule to indicate a namespace change in contrast to a thin rule to break up different method descriptions that can be difficult to scan.
- Left Justified Everything - Humans read from left to right, centered content is more laborious.
- Page grouped items to encourage sonner page breaks if the break happens at the beginning of a group of content (e.g. I don't want the heading of a section by itself at the bottom of a page and the beginning of its contents naked and without context on the following page.)

### API Reference

The API generation pipeline is roughly:

- Develop documents the code via type hints and docstrings utilizing an expanded google style documentation. (Extensions are WIP for now.)
- The `docs/builders/api` process is then responsible for extracting the docstrings and other syntactic artifacts via griffe integration. The `docs/builders/api` process' outputs is a variant of CommonMark markdown matching the requirements and attributes listed above.
- The generated API documentation is then rendered into a final product via either the pandoc build process or the docusaurus build process.
- Note: The output of the `docs/builders/api` is intended to be checked into the code base since users/developers should be able to reference markdown as documentation as-is.

### API Reference Markdown Patterns

- `<div class="namespace-rule" id="mylib.network"></div>` - A thick horizontal rule, indicating a new namespace.

- `<a id="mylib.network"></a>` - An anchor used to indicate the jump destination for the namespace or member on the page.

- `# network` - Headings can optionally be used. When headings are used, they are included in table of contents.

- `<small>``mylib.network``</small>` - Use for printing small fully qualified declarations beneath headers.

- The following is an example of a docstring from a class. It has a description followed by tables for non-method members and a table for method members. Each table should have hyperlinks to descriptions for the relevant members.

    ```md
    Core networking utilities for connection management, retry logic, and data
    transport. This module provides the foundational layer for all client-server
    communication within MyLibrary.

    **Attributes**

    | Name                                                | Type    | Default | Description                                 |
    | --------------------------------------------------- | ------- | ------- | ------------------------------------------- |
    | [`DEFAULT_TIMEOUT`](#mylib.network.DEFAULT_TIMEOUT) | `float` | `30.0`  | Global socket timeout in seconds.           |
    | [`MAX_POOL_SIZE`](#mylib.network.MAX_POOL_SIZE)     | `int`   | `10`    | Maximum concurrent connections in pool.     |
    | [`RETRY_BACKOFF`](#mylib.network.RETRY_BACKOFF)     | `float` | `1.5`   | Exponential backoff multiplier for retries. |

    **Functions**

    | Name                                                | Description                                   |
    | --------------------------------------------------- | --------------------------------------------- |
    | [`connect()`](#mylib.network.connect)               | Open a managed connection to a remote host.   |
    | [`ping()`](#mylib.network.ping)                     | Check reachability without opening a session. |
    | [`get_pool_stats()`](#mylib.network.get_pool_stats) | Return current connection pool metrics.       |
    ```

- `<div class="member-rule"></div>` - Thinner rule for members.

- `<div class="member-name" id="mylib.network.DEFAULT_TIMEOUT"><code>DEFAULT_TIMEOUT</code></div>` - Member name

- `<div class="none"> TODO: Make these links </div>` - Use display non for comments since `<!-- -->` and `{/* /*}` are mutually exclusive.

- `<div class="pagegroup"> ... content ... </div>` - Use page group to encourage appropriate page breaks.

  - page breaks should probably have ending documented: `</div><div class="none">end of network pagegroup</div>`

- `<div class="pagebreak"></div>` - Explicit page break (useful if you want classes to always start on new page)

- `<div class="h1-style">RetryPolicy</div>` - Decorate text like a heading, but without the implicit behavior of a heading (e.g. TOC inclusion)
