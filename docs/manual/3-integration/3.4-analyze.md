## 3.4 Analysis API

When you ask yannt to analyze an artifact, you invoke a **procedure** — a named unit of analysis logic — by requesting that it run, along with whatever inputs it requires. Procedures, and the registry of building blocks they are assembled from, are defined either by a configuration file or by arguments at invocation time.

Invoking a procedure doesn't run any analysis directly. Instead, it creates an **AnalysisProcess**: a runtime object that will hold one instance of every step the procedure is made of, plus the results those steps produce. Before anything executes, the process performs a dependency sort (i.e. topological sort) over the steps, so that each one runs only after everything it depends on has already produced its output. This is the first place the model is worth pausing on: the steps aren't a flat list or a fixed sequence you write by hand, they're a dependency graph, and the process derives the order at runtime from the dependencies you declared rather than from an order you specify.

The individual steps in that graph are called **AnalysisFactors**. A factor is a unit of code that derives some new piece of knowledge from the outputs of other factors — for example, taking a parsed structure and computing a metric from it. Each factor declares one or more dependencies, and those dependencies are simply other factors whose output it needs as input.

Every graph has to start somewhere, and that's the role of **AnalysisInput**, a specialized factor with no upstream factor dependencies. Instead of depending on other factors, an AnalysisInput depends on input supplied directly by the user. In practice, the first inputs are usually the target artifacts themselves (model files for instance) and the first real factors are typically the ones that parse those files into **pparse result trees**, which downstream factors then consume.

As the process runs each factor in dependency order, it stores that factor's output for later use. By the time every factor has executed, the AnalysisProcess holds the complete set of results from the whole graph. At this point the process is handed back to the user. If you asked for a **report** rather than the raw process, one more step happens: an **AnalysisReport** filters and formats that result set down to what you actually asked to see. Without a report, what you get back is the unfiltered output of every factor, in an associative array. While accurate, all results are not built for a person to read.

It's worth being explicit about why factors are organized this way rather than simply being run in the order a user lists them. A graph-with-inferred-order means the same factor can be reused as a dependency by multiple other factors without re-running it, and means procedures can be merged or reordered without the author having to manually re-sequence anything — the dependency declarations are the only ordering authority. The tradeoff is that you can't directly control execution order; you can only control it indirectly, through what depends on what.

One more distinction matters once you start composing procedures: an **AnalysisProcedure** is not the graph of running factors — it's the graph of factor *classes*. It defines which kinds of factors exist and how they depend on each other, but it holds no factor instances and no results. That separation is what lets a single procedure definition be reused across many runs, merged with other procedures, or optimized, without ever touching a previous run's state. When you invoke a procedure, it sorts its factor classes and uses that sort to initialize an AnalysisProcess, which is the object that actually owns live factor instances and their results.

Finally, all of these object classes: AnalysisFactor, AnalysisInput, AnalysisProcedure, and AnalysisReport are registered somewhere, and that registry is the **AnalysisFramework** (the name is still under consideration). It's best thought of as a namespace: a scope in which a given set of factors, inputs, procedures, and reports are known to each other and available to be assembled into procedures.
