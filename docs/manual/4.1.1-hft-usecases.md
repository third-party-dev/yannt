# Huggingface Transformers Use Cases

The Huggingface platform provides a transformers library that contains all of the models for the various transformer based models that you'll find referenced in the various config.json files amongst its repository. The difference between all the models on the Huggingface platform becomes purely based on the parameters and configuration arguments provided to this transformers library.

The library is primarily designed to take in some references to a repository and then will dynamically go out and download the associated parameter file for the model. My goals do not require the fully trained models. All I want is the structure of a serialized model, therefore we've written some code to extract only the model and fill in the parameters with random or ones to get an idea of the structure without having to download gazillions of bytes from the internet.

The tool that can extract and rebuild untrained models from the huggingface transformers library is called `hft` as the CLI command.

## Installation

At the moment, there is no published wheel for this tool. It is recommended to `cd misc/hft` then within the hft package folder, run `./scripts/init-dev.sh`. This will create a `venv` python environment with the `hft` package installed in place.

To re-activate the environment after initialization: `. ./cache/venv/hft/bin/activate`.

## Use Case: Generate _untrained_ models with hft

### Generate (params only) PyTorch file with hft

PyTorch files are fragile to serialize because the destination parser needs to match many aspects of the source, including code, library, and interpreter versions in a lot of cases. To make PyTorch files more stable across versions of models, so long as a model defines the same tensor names and shapes, you can tell PyTorch to only export the weights (or the `state_dict()`) of a loaded model. The result is a PyTorch file the contains application data  similar to the application data in a Safetensors, but in PyTorch pickle and PyTorch serialization format.

```sh
hft create --type AutoModel --model bert --pytorch_params_path ./yannt/models/bert/pt
```

### Generate PyTorch file with architecture with hft

A standard "pickle all the things" PyTorch serialization of the model.

```sh
hft create --type AutoModel --model bert --pytorch_path ./yannt/models/bert/pt
```

### Generate Safetensors (with config.json) with hft

A safetensors export of the parameters (`state_dict()`) of the model.

```sh
hft create --type AutoModel --model bert --safetensors_path ./yannt/models/bert/safetensors
```

### Generate ONNX with hft

Note: **NOT IMPLEMENTED FOR GENERAL USE**

A ONNX export of the given model.

Note: ONNX implicitly include the compute graph of the model. Not all Huggingface defined models are ONNX exportable. The inability to serialize the compute graph comes from the fact that there are sometimes dynamically generated operations based on results from previous operations. It can also needlessly occur because contributors haven't wrapped all of their data structures in torch.nn wrappers appropriately.

```sh
hft create --type AutoModel --model bert --onnx_path ./yannt/models/bert/onnx
```

### Generate an Export IR (intermediate representation) with hft

Runs `torch.export.export(model, input_ids)`. The output can be used to perform a number of analysis operations on the model.

```sh
hft create --type AutoModel --model bert --export_path ./yannt/models/bert/ir
```

## Generate graph outputs of transformers models with hft

In the export command, we can export the IR of a PyTorch model. Instead of exporting the file and then figuring out what to do, we can use `hft` to do some interpretations for us.

In general, we're using `exported = torch.export.export(model, input_args)`, and then running one of the analysis operations on the data:

- **human_ir** - `exported.graph_module.print_readable()`
- **compiler_ir** - `exported.graph_module.graph.print_tabular()`
- **schema** - `exported.graph_signature`
- **nodes** - `exported.graph_module.graph.nodes` with meta in a list format
- **graphviz** - `exported.graph_module.graph.nodes` in dot notation.
- **drawer** - FxGraphDrawer SVG of Graph

  ```python
  from torch.fx.passes.graph_drawer import FxGraphDrawer
  drawer = FxGraphDrawer(exported.graph_module, "exported_model")
  drawer.get_dot_graph().write_svg('path/to/my.svg')
  ```

- **coverage** - Python line use coverage of the (auto detected) python model files.

_Note: These actions can be performed on any fully PyTorch parsed files (using Python's unpickle). Considering adding a "input torch" argument as a replacement for "--model" and "--type" as an option. **TBD**._

### Use Case: Generate graph graphviz output with hft

`hft` will use the exported graph nodes to generate a graphviz friendly dot notation of the graph.

```sh
hft graph --type AutoModel --model bert --as graphviz --input ones
```

## Use Case: Breakpoint for in-depth inspection

In many of the above command, one can use the `--breakpoint` argument on the `hft` command to drop into a PDB session before the instance closes. This enables developers to inspect the python objects as they exist in the memory of the interpreter without staging a bunch of boilerplate python code.

```text
$ hft --breakpoint create --type AutoModel --model bert
Loading PyTorch and Transformers.
Indexing all of the transformer types available. (Takes a moment.)
Locals: ['args', 'os', 'Path', 'tmodel']
> /opt/data/thirdparty-ws/yannt_transformers/src/thirdparty/yannt/transformers/cli.py(147)transformers_create()
-> breakpoint()
(Pdb) type(tmodel.model)
<class 'transformers.models.bert.modeling_bert.BertModel'>
(Pdb)
```

Notice:

- We don't have to specify an export output.
- The actual model is stored as `tmodel.model`.
- All the available local variables are dumped before the breakpoint:

  ```text
  Locals: ['args', 'os', 'Path', 'tmodel']
  ```
