## 3.6 Pparse Lazy Parsers

The `lazy` package contains the format-specific parsers that do the actual work of turning raw bytes into the `Node` tree that the view layer exposes. If the view package is a public simplification, the lazy package is the engine underneath it. Understanding this layer is useful when implementing recursive parsing into multiple formats contained within each other from untrusted data.

Each format has its own subpackage. Every subpackage exports one function: `configure_pparser(**kwargs)`. That function is the entry point for the entire layer.

### 3.6.1 The configure_pparser factory

When a view calls something like `configure_pparser(ext_list=['.onnx'], init_msgtype='.onnx.ModelProto', ...)`, it does not get back a parser instance, it gets back a **Parser class**. That class is defined inside `configure_pparser` and closes over the kwargs. Calling `configure_pparser` with different arguments produces different classes: one that matches `.onnx` extensions and starts from `ModelProto` message type, another that matches `.pb` and starts from some user-supplied message type. Instantiating either class produces a parser that already knows its schema and its target extension.

The reason for returning a class rather than an instance is that the class needs to be instantiated once per `Extraction` — one instance per file. The configuration (schema, extension list, starting message type) is shared across all files parsed with the same settings, so it belongs in the class closure rather than in any individual instance.

The returned `Parser` class has three things the framework cares about:

- `match_extension(fname)` — returns `True` if the filename extension signals this parser can handle the data. Used by auto-detection. (Note: Unused by view package.)
- `match_magic(cursor)` — returns `True` if the file's leading bytes identify the format. Used as a fallback when extension matching fails or is unreliable. (Note: Unused by view package.)
- `make_root_node(parent=None)` — creates and returns the root `Node` for an `Extraction`, with its initial parser state already set.

`make_root_node` is where parsing begins. It instantiates a `Node` around the extraction's `Reader`, associates the parser with that node, and sets the node's **NodeContext** to an initial **State**. At this point nothing has been read from the file: the node is a placeholder with an unloaded value and a pending state.

### 3.6.2 States and The Parsing Loop

A **State** is a small object with one method: `parse_data(node)`. When `Node.load()` is called, it enters a loop: it calls `state.parse_data(node)`, inspects the return value, and either continues or stops. The return value is one of two constants: `AGAIN` (keep going — the state machine transitioned but there is more to do) or `ASCEND` (this node is done, leave the loop and return control to the caller).

Inside `parse_data`, the state reads bytes from `node.ctx()`. The `NodeContext`, using the same `peek`, `read`, `skip`, and `seek` methods that any `Reader` provides. When it recognizes a complete token or field, it writes the result into `node._value`. When it encounters a structure that requires a child node (e.g. a JSON object or array, a protobuf `LEN`-encoded field, a flatbuffers table), it creates a new `Node`, sets its initial state, and appends it to `node.ctx()._descendants`. Then it transitions to the next state by calling `ctx._next_state(NewState)` and returns `AGAIN`.

The parent's `load()` processes the `_descendants` list as it builds up: for each child node registered during parsing, it calls `child.load()` recursively. This is what makes the traversal depth-first and what `RecursionControl` bounds — the decision to recurse into a child is made at the moment the child is discovered, before moving on to the next sibling.

```text
Node.load()
 └─ loop: state.parse_data(node) → AGAIN | ASCEND
      ├─ AGAIN: transition state, continue loop
      └─ ASCEND: for each child in ctx._descendants:
                     child.load()   ← recursive
```

This design means states are simple: each state handles exactly one parsing concern (e.g. a JSON number, a protobuf varint key, a flatbuffers vtable) and hands off to the next state cleanly. The loop in `load()` is generic and knows nothing about formats. The format logic lives entirely in the states.

### 3.6.3 NodeContext: per-node parser state

Every `Node` owns a **NodeContext**, which is the coupling between the node and its parser. The `NodeContext` holds the state stack, a `Reader` positioned at the node's start offset, a reference to the parent node, and a `_descendants` list for child nodes that need to be loaded next.

The base `NodeContext` is generic. Each format subpackage may define a `NodeContext` subclass that adds format-specific fields. The protobuf `NodeContext` adds `_type_desc`, which holds the schema descriptor for the message type the current node is decoding — without it, the parser cannot map a field number to a field name. The flatbuffers `NodeContext` adds `_vtable_offset`, `_vtable_size`, `_field_offsets`, and related vtable fields that the `FlatbuffersParsingVTable` state reads and the `FlatbuffersParsingTable` state consumes. The JSON `NodeContext` adds `_key_reg`, a scratch register for map keys that are parsed but not yet paired with a value.

A `NodeContext` subclass is specified when creating a `Node` via the `ctx_class` argument. `make_root_node` is responsible for passing the right context class; states that create child nodes are also responsible for passing it to `pparse.Node(reader, parser, ctx_class=NodeContext)`.

A `NodeContext` is allocated for every node. Once a node's value is fully loaded and the caller no longer needs to re-parse it, `node.clear_ctx()` releases the context and recovers the memory. The decision to call this is a policy decision for the parser, the framework does not call it automatically.

### 3.6.4 How formats differ

The three binary encoding strategies in use drive a different state machine structure.

**JSON** is not length-delimited. To know where an object or array ends, the parser must read through its contents. This forces depth-first parsing: when a `{` is encountered, the parser creates a map node and immediately descends into it; the map's closing `}` ends the descent. States cycle through: `JsonParsingMeta` (dispatch on next character) -> `JsonParsingString` / `JsonParsingNumber` / `JsonParsingConstant` / `JsonParsingWhitespace` -> back to `JsonParsingMeta`. When `{` or `[` is seen, a new child node is created and pushed onto `_descendants`; when `}` or `]` is seen, `ASCEND` is returned.

**Protobuf** is length-delimited. Every `LEN`-typed field carries an explicit byte count before its payload. This means the parser can read a field's tag, learn the field's name and type from the schema (`_type_desc`), and create a child `Node` whose `Range` is bounded to exactly those bytes, without reading the content yet. The child is appended to `_descendants` and the parent skips past its bytes before processing the next sibling field. This tag-first structure is what `ProtobufParsingTag` implements. Simple wire types (VARINT, I32, I64) are decoded inline and stored as scalars; `LEN` wire types become child nodes.

**Flatbuffers** uses vtables. A table in a flatbuffer does not list its fields sequentially; instead, each table carries a (mostly backwards) offset to a vtable that maps field indices to byte offsets within the table. The `FlatbuffersParsingVTable` state reads the vtable, builds a `_field_offsets` dict, and transitions to `FlatbuffersParsingTable`, which uses those offsets to seek to each field in turn. Simple fields are decoded in-place; fields that point to other tables, strings, or vectors create child nodes. Because the offsets are known upfront, field decoding within a table is random-access rather than sequential.

The difference between protobuf and flatbuffers from the parser's perspective is where the layout information lives: in protobuf it's in the byte stream (as varint length prefixes), in flatbuffers it's in the vtable (as u16 field offsets). JSON has no layout information at all — the parser discovers structure entirely by character inspection.

### 3.6.5 Adding a new format

A new format parser is a new subpackage under `lazy` that provides:

1. A `configure_pparser(**kwargs)` function that returns a `Parser` subclass.
2. A base `ParsingState` class and concrete state subclasses implementing `parse_data(node) -> int`.
3. Optionally, a `NodeContext` subclass if the format needs per-node fields beyond what the base provides.

The `Parser` subclass must implement `match_extension`, `match_magic`, and `make_root_node`. `make_root_node` creates the root `Node` with the format's initial state set via `root.ctx()._next_state(InitialState)`. States are responsible for creating child nodes and appending them to `ctx._descendants`; `Node.load()` handles the rest.
